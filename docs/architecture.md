# Архитектура

## Части системы

- **Next.js (App Router, TypeScript)** — единое приложение: и фронтенд, и бэкенд (API-роуты) в одном процессе.
  - `/book` — публичная страница записи: выбор услуги → мастера → даты и времени → контакты.
  - `/admin` — админка за паролем (cookie `admin_auth`, сверяется с `ADMIN_PASSWORD` из `.env`): записи, услуги, команда.
  - `/api/*` — REST-эндпоинты (`services`, `masters`, `availability`, `bookings`), которыми пользуется страница `/book` из браузера. Без ключа, открыты — так их использует публичный сайт.
  - `/api/bot/*` — те же данные и действия (`services`, `masters`, `availability`, `bookings`), но для бота: требуют заголовок `X-API-Key` (сверяется с `APP_API_KEY` из `.env`). Отдельные пути, чтобы не ломать публичный `/api/*`.
- **PostgreSQL** — поднимается локально через `docker-compose.yml`, том `proservice-db-data` хранит данные между перезапусками.
- **Prisma** — ORM и миграции (`prisma/schema.prisma`), плюс `prisma/seed.ts` для тестовых данных.
- **Клиентский Telegram-бот-администратор** (`bot_administrator/`) — отдельный процесс, Node.js/TypeScript, свой `package.json`. Роль ПОДДЕРЖКА (`bot_administrator/role.md`), характер общения — `bot_administrator/character.md`, база знаний — `../faq/faq.md`. Отвечает через OpenRouter (модель `google/gemini-2.5-flash`) с tool-use: сам решает, ответить по базе знаний или вызвать `/api/bot/*` и выполнить действие (показать услуги/слоты, оформить запись). Работает постоянно на сервере как systemd-сервис `bot-administrator` (не зависит от компьютера студента) — деплоится и перезапускается вместе с приложением через CI.

## Как части общаются

```
Браузер → Next.js (страницы + /api/*) → Prisma Client → PostgreSQL (Docker)
```

Страницы (`/book`, `/admin`) и API-роуты работают в одном приложении и напрямую вызывают Prisma — отдельного backend-сервиса нет. Внешние потребители (боты, MCP, интеграции с воркшопов) обращаются к `/api/*`.

```
                                   ┌─ FAQ (текстовый ответ)
Telegram → bot.ts (long polling) → OpenRouter (tool-use) ─┤
                    ↑                                     └─ tool_calls → apiClient.ts → /api/bot/* → Prisma → PostgreSQL
      системная инструкция: role.md + character.md + faq/faq.md
```

Бот — отдельный Node-процесс. На каждое сообщение собирает системную инструкцию (один раз при старте) + последние ~5 сообщений этого чата (`src/history.ts`) и отправляет в OpenRouter (`src/openrouter.ts`) вместе со списком инструментов (`src/tools.ts`: `get_services`, `get_masters`, `get_availability`, `create_booking`). Модель сама решает: отвечать по базе знаний (`faq.md`) или вызвать инструмент — тот бьёт в `/api/bot/*` через `src/apiClient.ts` (ключ и адрес — `APP_API_KEY`/`APP_API_URL` из `bot_administrator/.env`). Цикл «модель вызвала инструмент → получила результат → снова думает» повторяется, пока не будет готов финальный текстовый ответ (максимум 5 раундов на сообщение); результат пересказывается клиенту человеческим языком, а не сырым JSON.

Голосовые сообщения: `bot.on("voice")` скачивает аудио из Telegram в память (без временных файлов) и отдаёт в `src/transcribe.ts` — расшифровка через официальный SDK `assemblyai` (pre-recorded, модель `universal-2`, `language_detection: true` для ru/en). Расшифрованный текст дальше идёт той же веткой, что и обычное текстовое сообщение.

## Модель данных

`Service` (услуга) ↔ `Master` (мастер) — связаны через `MasterService` (many-to-many). У мастера есть `WorkingHour` (график по дням недели). `Booking` (запись) ссылается на услугу и мастера, хранит интервал `startAt`–`endAt` и статус (`CONFIRMED` / `CANCELLED` / `DONE`).

## Ключевые технические решения

- **Слоты считаются на лету, не хранятся.** `src/lib/availability.ts` берёт график мастера на нужный день недели и вычитает пересечения с активными бронями — свободное время не материализуется в БД.
- **Защита от двойной записи — на уровне API.** `POST /api/bookings` (и `/api/bot/bookings`) перед созданием брони ищет пересечение по времени среди не отменённых записей того же мастера и возвращает `409`, если конфликт есть (гонки возможны, но для учебного проекта это осознанно упрощено).
- **`/api/bot/*` — отдельная копия логики, не рефакторинг существующих `/api/*`.** Осознанный компромисс: не трогать работающие публичные роуты (риск сломать `/book`), взамен — небольшое дублирование кода между `/api/bookings` и `/api/bot/bookings`.
- **`bot_administrator/` исключён из сборки Next.js** (`tsconfig.json` → `exclude`). У него свой `node_modules` и своя система типов — без исключения `next build` пытался проверить типы файлов бота и падал на отсутствующих зависимостях.
- **На сервере есть swap (2 ГБ, `/swapfile`).** На боевом боксе всего ~1 ГБ RAM — без swap `npm ci`/`next build` временами падают с OOM (killed процессом ядра). Swap — постоянная страховка, а не разовая мера.
- **Админка — простой пароль в cookie, не полноценная авторизация.** Это осознанное упрощение под учебные цели; в `.env.example` это явно прокомментировано.
- **Один универсальный движок вместо готового домена.** Схема нейтральна («услуга + мастер + слот + запись»), а под конкретный домен (салон, автосервис, репетитор) переодевается через `seed.ts` — не через код.
- **Docker только для БД**, само приложение запускается локально через `npm run dev` — меньше инфраструктуры для учебных целей.
- **Бот — long polling, не webhook/websocket.** На некоторых VPS websocket не работает, поэтому `bot_administrator` опрашивает Telegram API по обычному HTTP.
- **У бота свой `package.json` и свой `.env`.** Отдельный процесс, отдельные секреты (`bot_administrator/.env`: `TELEGRAM_BOT_TOKEN`, `OPENROUTER_API_KEY`, `ASSEMBLYAI_API_KEY`) — не смешивается с `.env` основного приложения.
- **Бот на сервере — systemd-сервис, `.env` приходит из GitHub Secrets, не из git.** `bot_administrator/.env` исключён из rsync (как и `.env` основного приложения). При каждом деплое `.github/workflows/deploy-app.yml` пишет `bot_administrator/.env` на сервере из ОДНОГО секрета `BOT_ENV` (весь файл целиком, одной строкой в Secrets) — затем `npm ci` и `systemctl restart bot-administrator`. Юнит `bot_administrator/bot-administrator.service` — обычный файл в репозитории (не секрет, секретов не содержит), деплой копирует его в `/etc/systemd/system/` и перечитывает демон.
- **Все три внешних сервиса бота идут через курсовой прокси** (`TELEGRAM_API_BASE`, `OPENROUTER_BASE_URL`, `ASSEMBLYAI_BASE_URL` в `.env`, ключ потока — `BOOST_PROXY_KEY`) — прямые адреса недоступны с сервера в РФ. Ключи сервисов не меняются, прокси их только пробрасывает. Адреса читаются лениво (внутри функций, после `dotenv.config()`), а не в константах на верхнем уровне модуля — иначе `process.env` ещё не был бы заполнен на момент их вычисления (порядок исполнения ESM-импортов).
- **Ответы бота — строго по базе знаний и реальным данным API, без домысливания.** Системная инструкция явно запрещает выдумывать факты (цены, расписание) и особенно запрещает выдумывать id услуг/мастеров для вызова инструментов — они должны быть дословно скопированы из предыдущего ответа `get_services`/`get_masters` в этом же разговоре, не сгенерированы по памяти. Модели вроде `google/gemini-2.5-flash` время от времени всё равно ошибаются в этом (эмпирически найдено при тестировании) — API на бэкенде дополнительно валидирует id и возвращает `404`, если что-то не так; бот в этом случае обязан перезапросить `get_services`/`get_masters`, а не сразу сдаваться.
- **Температура модели понижена (0.2).** Это не творческий чат — важна не разнообразность, а то, чтобы бот не выдумывал занятость/расписание вместо вызова `get_availability`.
- **Память диалога — в памяти процесса, не в БД.** `src/history.ts` хранит последние ~5 сообщений на чат в `Map`; при перезапуске бота история теряется (учебное упрощение).
- **Сбои внешних сервисов не должны доходить до клиента как технические ошибки.** У всех внешних вызовов бота (OpenRouter, AssemblyAI, `/api/bot/*`, скачивание файла из Telegram) есть таймаут (`AbortController`) — зависший сервис не вешает диалог навсегда. `src/errors.ts` классифицирует сбой (`timeout` / `rate_limit` / `unavailable` / `bad_input`) и даёт понятное сообщение клиенту на русском — без стектрейсов и сырых текстов ошибок API (те уходят только в лог сервера). `apiClient.ts` даже сетевой сбой превращает в обычный `{ok:false, ...}`, а не исключение — модель получает понятный повод сказать клиенту «сервис сейчас недоступен», вместо того чтобы уронить весь ответ. `safeSend()` в `bot.ts` не даёт упасть самому процессу, если отправка сообщения в Telegram тоже не удалась; `process.on("unhandledRejection"/"uncaughtException")` — страховка последнего рубежа, чтобы сбой в одном диалоге не положил бота для всех остальных.
- **API приложения (`/api/*` и `/api/bot/*`) оборачивает обращения к Prisma в try/catch** (`src/lib/apiErrors.ts`) — при недоступности БД клиент получает чистый `503 {error: "..."}`, а не страницу ошибки Next.js со стектрейсом. Валидация входа (обязательные поля, корректный JSON, существование услуги/мастера, конфликт времени) была устойчивой и раньше — не переписывалась.
