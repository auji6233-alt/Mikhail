# Архитектура

## Части системы

- **Next.js (App Router, TypeScript)** — единое приложение: и фронтенд, и бэкенд (API-роуты) в одном процессе.
  - `/book` — публичная страница записи: выбор услуги → мастера → даты и времени → контакты.
  - `/admin` — админка за паролем (cookie `admin_auth`, сверяется с `ADMIN_PASSWORD` из `.env`): записи, услуги, команда.
  - `/api/*` — REST-эндпоинты (`services`, `masters`, `availability`, `bookings`), которыми пользуется страница `/book` из браузера. Без ключа, открыты — так их использует публичный сайт.
  - `/api/bot/*` — те же данные и действия (`services`, `masters`, `availability`, `bookings`), но для бота: требуют заголовок `X-API-Key` (сверяется с `APP_API_KEY` из `.env`). Отдельные пути, чтобы не ломать публичный `/api/*`.
- **PostgreSQL** — поднимается локально через `docker-compose.yml`, том `proservice-db-data` хранит данные между перезапусками.
- **Prisma** — ORM и миграции (`prisma/schema.prisma`), плюс `prisma/seed.ts` для тестовых данных.
- **Клиентский Telegram-бот-администратор** (`bot_administrator/`) — отдельный процесс, Node.js/TypeScript, свой `package.json`. Роль ПОДДЕРЖКА (`bot_administrator/role.md`), характер общения — `bot_administrator/character.md`, база знаний — `../faq/faq.md`. Отвечает через OpenRouter (модель `google/gemini-2.5-flash`), системная инструкция собирается из role.md + character.md + faq.md; консультация по услугам работает, сама запись (вызов `/api/bookings`) — следующий шаг.

## Как части общаются

```
Браузер → Next.js (страницы + /api/*) → Prisma Client → PostgreSQL (Docker)
```

Страницы (`/book`, `/admin`) и API-роуты работают в одном приложении и напрямую вызывают Prisma — отдельного backend-сервиса нет. Внешние потребители (боты, MCP, интеграции с воркшопов) обращаются к `/api/*`.

```
Telegram → bot_administrator/src/bot.ts (long polling) → OpenRouter (google/gemini-2.5-flash) → ответ клиенту
                                                              ↑
                                        системная инструкция: role.md + character.md + faq/faq.md
```

Бот — отдельный Node-процесс. На каждое сообщение собирает системную инструкцию (один раз при старте) + последние ~5 сообщений этого чата (`src/history.ts`) и отправляет в OpenRouter (`src/openrouter.ts`). Отвечает строго по базе знаний — если ответа в `faq.md` нет, модель обязана честно сказать, что не знает, а не придумывать. Для самих действий (показать услуги/слоты, оформить запись) у бота есть защищённый `/api/bot/*` (см. выше) — код вызова из бота появится на следующем шаге.

## Модель данных

`Service` (услуга) ↔ `Master` (мастер) — связаны через `MasterService` (many-to-many). У мастера есть `WorkingHour` (график по дням недели). `Booking` (запись) ссылается на услугу и мастера, хранит интервал `startAt`–`endAt` и статус (`CONFIRMED` / `CANCELLED` / `DONE`).

## Ключевые технические решения

- **Слоты считаются на лету, не хранятся.** `src/lib/availability.ts` берёт график мастера на нужный день недели и вычитает пересечения с активными бронями — свободное время не материализуется в БД.
- **Защита от двойной записи — на уровне API.** `POST /api/bookings` (и `/api/bot/bookings`) перед созданием брони ищет пересечение по времени среди не отменённых записей того же мастера и возвращает `409`, если конфликт есть (гонки возможны, но для учебного проекта это осознанно упрощено).
- **`/api/bot/*` — отдельная копия логики, не рефакторинг существующих `/api/*`.** Осознанный компромисс: не трогать работающие публичные роуты (риск сломать `/book`), взамен — небольшое дублирование кода между `/api/bookings` и `/api/bot/bookings`.
- **Админка — простой пароль в cookie, не полноценная авторизация.** Это осознанное упрощение под учебные цели; в `.env.example` это явно прокомментировано.
- **Один универсальный движок вместо готового домена.** Схема нейтральна («услуга + мастер + слот + запись»), а под конкретный домен (салон, автосервис, репетитор) переодевается через `seed.ts` — не через код.
- **Docker только для БД**, само приложение запускается локально через `npm run dev` — меньше инфраструктуры для учебных целей.
- **Бот — long polling, не webhook/websocket.** На некоторых VPS websocket не работает, поэтому `bot_administrator` опрашивает Telegram API по обычному HTTP.
- **У бота свой `package.json` и свой `.env`.** Отдельный процесс, отдельные секреты (`bot_administrator/.env`: `TELEGRAM_BOT_TOKEN`, `OPENROUTER_API_KEY`) — не смешивается с `.env` основного приложения.
- **Ответы бота — строго по базе знаний, без домысливания.** Системная инструкция явно запрещает модели выдумывать факты, которых нет в `faq/faq.md`; при отсутствии ответа бот честно говорит об этом.
- **Память диалога — в памяти процесса, не в БД.** `src/history.ts` хранит последние ~5 сообщений на чат в `Map`; при перезапуске бота история теряется (учебное упрощение).
